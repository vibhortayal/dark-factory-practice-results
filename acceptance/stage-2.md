# Stage 2 acceptance map (pocketful)

Source: `pocketful/spec/stage-2.md` (kickoff checkout), which keeps every stage-1 requirement in
force. Rows of `acceptance/stage-1.md` (A1-J3) all still apply to `stage-2/`, except where a row
below changes them; row K1 carries them. "UI test" means a browser check (Playwright/Chromium)
against the running container; "API test" a black-box HTTP check. Rows marked **[reading]** are
Architect choices where the specification is open, with the reason. The supplied checks cover
only part of this map.

## K. Carry-over and delivery

| Row | Requirement | Check |
|---|---|---|
| K1 | Every row of the stage-1 map (A1-J3) holds for `stage-2/`, with stage-2 changes: `/me` gains fields (M1), payments gain `authorization_id` (N6), `insufficient_funds` is judged against `available` (M3), seven idempotent paths (N1), and stage-1 row J1 is replaced by K4. | Harness `--stage 2` runs suite 1 against `stage-2/`; Verifier reruns its stage-1 list against the stage-2 image |
| K2 | `stage-2/` is the accepted `stage-1/` copied and extended (no `.git` inside, no symlinks), complete and buildable on its own with its own `Dockerfile` and `RUN.md`; `stage-1/` itself is not modified. | `git diff` of `stage-1/` empty since d02b8f6; clean build of `stage-2/` |
| K3 | All UI assets (HTML, scripts, styles, fonts, icons) are served from the image; nothing is fetched from another origin at run time. Limits of stage-1 §2 still hold (2 vCPU, 2 GiB, 60 s start, 50 in flight, 5 s per request). | Isolated-mode harness run; browser network log shows same-origin requests only |
| K4 | `stage-2/` implements stage 2 only, nothing from a later stage. | Harness `--stage 2` prints `claimed stage: 2 on the shipped checks`; its stage-3 overshoot line fails |
| K6 | **[reading]** Time: each request reads the clock once and every timestamp it assigns and every expiry decision it makes uses that one instant. Server-assigned timestamps (`created_at`, `committed_at`, `expires_at`) are true instants with microsecond precision in a fixed-width form (`2026-09-24T13:10:00.123456+00:00`, always six fractional digits, numeric offset), not rounded to seconds, and never go backwards from one write to the next (a later write never carries an earlier timestamp). So `expires_at - created_at` is exactly `authorization_ttl_seconds` for every authorization, a hold is open strictly before `expires_at` and expired at or after it, and a capture's payment is never timestamped before its authorization. Timestamps that arrive in a fixture or an import are kept exactly as given. Reason: the spec says "`expires_at` is `created_at` plus `authorization_ttl_seconds`" and "an authorization whose `expires_at` is at or before now is `expired`"; whole-second rounding makes a short lifetime up to a second too short or too long. | API test: 20,000 creations all with the exact difference; ttl 1 hold open at +0.5 s and expired at +1.1 s; in-image test with a stepped clock |
| K5 | Supplied checks pass: from the kickoff checkout `.venv/bin/python -m harness run --track pocketful --repo ../band-work/result --stage 2 --out ../band-work/checks/<new-name>` (suites 1 and 2); final run with `--mode isolated`. | Harness output |

## M. Wallet model changes (spec "Authorizations and captures", "The existing API changes")

| Row | Requirement | Check |
|---|---|---|
| M1 | `GET /me` -> `{user_id, display_name, handle, balance, total, available, held, currency, minor_units}`; `balance == total` always; `held` = sum of remaining amounts of open, unexpired holds where the user is payer; `available = total - held`, never negative. With no open holds everything behaves as in stage 1. | API test |
| M2 | Sum of all `total` always equals the seeded total; a hold moves no money; payments, settlements and captures move it. | Sum over users after every burst |
| M3 | `available` never negative, at every read. | M4 | `POST /payments` stays an immediate transfer (no intermediate hold, nothing in `/authorizations`); paying a request stays immediate; `POST /splits` unchanged. | API test |
| M5 | Concurrent requests give the result of some serial order, and every invariant holds at every read. | Concurrent captures of one hold (same and different keys), capture vs void, capture vs expiry, authorizations vs payments at 50 in flight |

## N. Authorizations API

| Row | Requirement | Check |
|---|---|---|
| N1 | Seven idempotent write paths: stage 1's five plus `POST /authorizations` and `POST /authorizations/{id}/capture`. All stage-1 F rows (first use 201, replay 200 same body, reuse 409, user and path scope, failed key reusable, concurrent identical -> one 201, replay after change, claimed key resolved before validation) apply to each; missing key 400 `missing_idempotency_key`, over-long key 422. | API test on both new paths |
| N2 | Fixture: `authorization_ttl_seconds` (default 600 when omitted; if supplied must be a positive integer, otherwise reset is 422 with nothing changed) and `authorizations` array (omitted = empty) of `{id, from_user_id, to_user_id, amount, note, visibility, status, expires_at}`; seeded `status` is `open`, `captured`, `voided` or `expired`; only `open` holds anything; seeded holds keep their own absolute `expires_at`. User `balance` is still `total`; `available` is derived. | API test: reset, `GET /me`, `GET /authorizations` |
| N3 | A sum of seeded unexpired open holds larger than that user's `balance` -> 422 `validation_failed` from reset, nothing changed. Equal to balance is accepted (available 0). Seeded open holds already expired do not count. **[reading]** other invalid authorization entries (unknown user id, bad status, unparseable `expires_at`, amount not a positive integer, from == to) are also 422 with nothing changed. | API test |
| N4 | Expiry by the clock: an authorization whose `expires_at` is at or before now is `expired` and holds nothing, on every read and write, even if no request happened at the deadline: `GET /authorizations` shows `status: "expired"`, `GET /me` includes the released remainder in `available`. Works for seeded expiry times an hour or more in the past or future and for short TTLs on created ones. | API test with `authorization_ttl_seconds: 1` and with a seeded past `expires_at` |
| N5 | `POST /authorizations {to_handle, amount, note?, visibility?}` (caller is payer) -> 201 `{authorization_id, from_user_id, from_handle, to_user_id, to_handle, amount, captured_amount: 0, remaining_amount, currency, note, visibility, status: "open", expires_at, payment_id: null, payment_ids: [], created_at}`; `expires_at = created_at + authorization_ttl_seconds`; defaults as `POST /payments`. Rejections: `available` below `amount` 409 `insufficient_funds` (equal succeeds); amount below 1, above 1000000000 or not an integer 422; own handle 422 `self_payment`; note over 200 characters or bad visibility 422; unknown handle 404. Order of checks as stage-1 row D9. | API test |
| N6 | An open authorization is not a feed item and never appears in `GET /activity`. Every payment object now carries `authorization_id` (null unless created by a capture) next to `request_id` and `settlement_id`. | API test |
| N7 | `POST /authorizations/{id}/capture {amount?, final?}`: receiver only; 201 with the created payment in the `POST /payments` shape, `authorization_id` set, `request_id: null`, `amount` = captured amount, `note` and `visibility` copied from the authorization, sender = payer, receiver = caller; appears in the feed by the ordinary rule. `amount` defaults to the remaining amount. `{}` and `{"amount": 2000}` are different bodies for replay (409 `idempotency_key_reuse` across them). **[reading]** an entirely empty body is treated as `{}`, as on pay. | API test |
| N8 | Default (final) capture: status becomes `captured`, `captured_amount` and `payment_id` set, uncaptured remainder released to the payer's `available` in the same step (capture 1500 of 2000 -> payer total -1500, held -2000). A second capture after a final one is 409 `authorization_not_open`. | API test |
| N9 | Extended mode: `final` is a boolean, default `true`. `final: false` with a remainder left keeps status `open` and the remainder held; further captures allowed up to the remainder; capturing the whole remainder closes it even with `final: false`; a final capture closes it and releases the remainder. `captured_amount` is cumulative; `payment_id` is the latest capture; `payment_ids` lists every capture in order; `remaining_amount` is the amount still held, zero when closed (captured, voided or expired). Cumulative captures never exceed the authorized amount; each idempotent capture moves money once. **[reading]** a non-boolean `final` is 400 `malformed_request` (wrong JSON type, not among the 422 exceptions). | API test: 700 non-final, 800 non-final, then remainder; over-capture; concurrent partial captures with different keys never exceed the amount |
| N10 | Capture rejections: not `open` 409 `authorization_not_open`; `expires_at` at or before now 409 `authorization_expired`; `amount` above the uncaptured remainder 422 `capture_exceeds_authorization` (remainder itself accepted, remainder + 1 refused); `amount` below 1 or not an integer (string, boolean, null, fraction) 422 `validation_failed`; caller not the receiver 403 `forbidden` (payer and third parties alike); unknown authorization 404. **[reading]** order: body validation (422/400), then 404, 403, then state (`authorization_expired` for an authorization that is expired by the clock or seeded `expired`; `authorization_not_open` for `captured` or `voided`), then `capture_exceeds_authorization`. A capture amount has no 1000000000 rule of its own: anything above the remainder is `capture_exceeds_authorization`. | API test |
| N11 | `POST /authorizations/{id}/void`: payer only, no idempotency key; 200 with the authorization, `status: "voided"`, hold released; already voided -> 200 current state; `captured` or `expired` -> 409 `authorization_not_open`; caller not the payer (receiver or third party) -> 403 `forbidden`; unknown -> 404. Void or expiry of a partially captured authorization releases only the remainder and keeps all capture records (`captured_amount`, `payment_ids`, the payments themselves). | API test |
| N12 | `GET /authorizations` -> `{authorizations, has_more}`; only authorizations where the caller is payer or receiver; newest first by `created_at`; `direction` = `outgoing` (caller is payer) / `incoming` (caller is receiver) / absent = both; `status` one of `open`, `captured`, `voided`, `expired` or absent; an authorization expired by the clock matches `expired`, never `open`; unknown `direction`/`status` 422; `limit`/`offset`/`has_more` exactly as `GET /requests` (stage-1 row D7). Settlement operators get no extra visibility. | API test |
| N13 | Export/import and reset keep or clear authorizations like everything else: holds, statuses, `expires_at`, capture records, TTL and the idempotent responses of the two new paths survive export -> import into a fresh container; ids and timestamps are not regenerated. | API test |

## O. Formatting and amount input

| Row | Requirement | Check |
|---|---|---|
| O1 | Formatted amount = decimal with exactly `minor_units` places, one space, currency code: `100.00 EUR`, `0.05 EUR`, `1200 JPY` (no decimal point for 0), `1.500 BHD`. No sign, no thousands separator. Used wherever a test id says "exactly the formatted amount". | UI test with EUR, JPY, BHD fixtures |
| O2 | Amount inputs take a decimal string as a person types it and submit minor units: with 2 minor units `15.00` and `15` -> 1500, `15.5` -> 1550. Non-numeric input or more than `minor_units` decimal places (`15.005`; any decimal point for JPY) shows the form's error element and sends **no** request; nothing is rounded. Conversion is exact (string arithmetic, no floating point: `0.29`, `1.10`, `1000000.00` convert exactly). Applies to `pay-amount`, `request-amount`, `split-amount`, `authorize-amount`, `authorization-capture-amount-{id}`. | UI test watching network requests |

## P. Wallet and pay screen `/`

| P10 | Authorize form: `authorize-handle`, `authorize-amount`, `authorize-note`, `authorize-visibility`, `authorize-submit`, same input rules as the pay form; `authorize-error` when refused, including insufficient available funds. | P11 | **[reading]** Every write the UI sends through an idempotent path (request, split, authorize, pay-request, capture) keeps one key for as long as its inputs are unchanged, like the pay form, so a double click or a retry after a lost response cannot act twice. | UI test: double-click each submit |
